Reference: every value

This chapter is a set of lookup tables. Use it when you see a word, a badge, a colour, a status or a number in RAGGuard and want to know exactly what it means and what to do about it. It covers the issue types, severities, statuses, document states, vector classes, audit runs and their numbers, the health score, repair plans, connection states, test results, alert outcomes, settings, the HTTP API, limits, and a glossary. The explanations of whole pages are in the other chapters; this one is for looking things up. New to the vocabulary? Start with Concepts you need.

Colours below are the ones the interface uses. Green means good, amber means look at it, red means act, blue means in progress or informational, grey means neutral.

Issue types

There are eleven issue types. The label is what you see in the interface; the internal name is what appears in the API, in exports and in the Type filter's address.

LabelInternal nameSeverity and how it is decidedSystems involvedRecommended actionWhat it means and what to do
Missing embeddingsmissing_embeddingHigh. Critical when the manifest claims success (a success-like status, or an indexed chunk count above 0). Not raised while the document is inside the grace period.Amazon S3, QdrantFull reindexThe document exists in S3 but the index holds nothing for it, so users get no answer from it. Re-process the document. If the pipeline reported success, find out why it wrote nothing.
Partial indexpartial_indexHigh. Critical when the manifest claims success. Medium when only gaps in the chunk numbers suggest it ("suspected"). Skipped when the document is stale.Qdrant, PostgreSQLRe-embed missing chunksOnly some of the expected chunks are indexed, so answers can be silently incomplete. Re-embed the missing chunks (a full rebuild is also safe).

Metadata problems

A Metadata mismatch issue lists one or more of these problems under Problems found in its evidence.

CodeSeverityMeaning
missing_payload_fieldsMediumVector payloads lack fields you require (by default document_id, source_hash, and tenant_id once there is more than one tenant)
untracked_in_manifestMediumVectors exist for a current document but the manifest has no row for it
manifest_count_mismatchMediumThe manifest says N chunks are indexed and the index holds a different number. Hidden when a partial index already explains it.
acl_mismatchHighVectors carry a different access-control hash than the manifest, so permissions may be wrong at query time
manifest_lags_indexLowThe index is current but the manifest still records an older source hash
manifest_version_mismatchLowThe manifest's indexed version differs from the source version although the content hashes agree
status_failed_but_indexedLowThe manifest status says failed although the document is indexed
unattributed_vectorsHighCollection level: points that carry no document id. See below.

Collection-level findings

Two findings belong to a whole Qdrant collection, not to one document. In lists the document column reads "Whole collection" (or "Whole tenant" in some run lists). They cannot become repair plans. Fix them in your own systems, then audit again.

FindingTypeSeverityMeaning
Vectors without a document idMetadata mismatchHighN points in a collection carry no document id, so they cannot be matched to any document
Collection vector size does not match the target embedding modelPipeline driftCriticalThe vector size of a collection differs from Embedding dimensions in Settings, Pipeline, so queries embedded with the target model cannot match it

Repair actions

Internal nameLabel shownWhat it means
reindex_fullFull reindexRe-process the whole document from the latest source: parse, chunk, embed and write, then update the manifest
reindex_chunksRe-embed missing chunksRe-embed only the missing chunks (a full rebuild is also safe)
cleanup_vectorsRemove old vectorsRemove the listed vectors, only after the replacements are verified and an operator approves
fix_metadataFix metadataCorrect the manifest or the payload; no re-embedding
investigateNeeds a humanNo automatic repair exists; someone has to look

How a repair plan chooses actions for one document:

  • Missing, stale, drifted or empty-embedding issues give Full reindex.
  • Otherwise, a partial index gives Re-embed missing chunks.
  • A metadata mismatch adds Fix metadata only when there is no Full reindex (a full reindex already rewrites the manifest).
  • Superseded, duplicate, orphan and tenant-mismatch issues set the "remove old vectors" flag, which becomes Remove old vectors after verification.
  • An orphan manifest row and any collection-level finding give no automatic action (Needs a human).

Issue statuses

StatusBadgeMeaningHow it changes
OpenAmberThe audit found it and it has not been fixed or ignoredBecomes Resolved when an audit that covers the document no longer finds it. Becomes Ignored when you ignore it.
ResolvedGreenAn audit no longer finds itBecomes Open again (its "Reopened" count goes up) if a later audit finds it again
IgnoredGreyYou decided to accept it and, optionally, said whyStays Ignored, even if later audits still find it, until you click Reopen

An issue keeps one identity across audits: the same problem on the same document is the same row, and its Seen number counts the audits that saw it. A scoped audit only resolves issues inside its own scope.

Document statuses

The audit gives every document one of five statuses. They are shown under Document status on Overview, in the Status filter on Documents, and as the tabs of the Reconciliation documents table.

StatusColour (Overview bar)MeaningHow it is decided
HealthyGreenSource, manifest and index agreeNo findings
DegradedAmberSearchable, with minor issuesThe worst finding is medium or low
BrokenRedSerious issues foundAt least one critical or high finding
PendingBlueStill being processedChanged or in flight within the grace period and no findings. Not judged yet.
OrphanedGreyDeleted at the source, vectors remainNot in the source, but vectors exist

"Needs attention" on Documents and Reconciliation means Degraded plus Broken. A document's status comes from what the audit finds, not from your Ignore decisions.

Document states

The Embedding status column on Documents (and the Status column in the Reconciliation documents table) is a simpler label derived from the status and the issue types, checked in this order.

StateColourHow it is derived
ProcessingBlueThe document status is Pending
Missing embeddingsRedThe document has a Missing embeddings issue
StaleAmberThe document has a Stale document version issue, or its status is Degraded
HealthyGreenThe status is Healthy
FailedRedThe status is Broken or Orphaned (and neither of the two rules above applied)

"Failed" does not mean a pipeline job failed. It means the audit found serious problems with the document, or that the document is an orphan. A Broken document with only, for example, a tenant mismatch shows as Failed.

Vector classes

While the index is scanned, RAGGuard gives every vector one class by comparing it with the live source and your target pipeline. You see the classes on the Chunks tab of a document after Inspect live.

ClassColourMeaningHow it is decided
FreshGreenMatches the current source and the pipelineIts hash (or, if it has none, its version) matches the source, and it does not conflict with the target pipeline
StaleAmberBuilt from an older version of the documentIts hash (or version) differs from the source's
OutdatedAmberCurrent content, built with an older pipeline setupHash matches, but a value it records conflicts with the target pipeline
UnknownGreyThe index does not say which version it isThe payload carries no hash and no version, so freshness cannot be established
OrphanRedThe document no longer exists at the sourceThe document is not in the source

Fresh and Unknown vectors count as live. The checks run in this order: Orphan, then Stale, then Outdated, then Fresh or Unknown.

Change counters

These five numbers describe what an audit changed compared with the audit before it. You see them as Since the previous audit on Reconciliation, as Last audit on Overview and as Changes in this audit on the run page. In the runs table the Changes column shows "N opened" and "N resolved".

Health score

Health score is the share of documents that are healthy, as a percentage: (Healthy documents + Pending documents) divided by all documents, rounded to one decimal place. Pending documents count as healthy because they are probably still being ingested.

ScoreBadge colour
90% and aboveGreen
70% up to just under 90%Amber
Below 70%Red
No score yetGrey, with a dash

Where it appears: the first card on Overview (from the latest state of all documents, so a scoped or verification audit that refreshes some documents can move it), the Health over time chart (one point per completed full audit), the Health column in Audit history, the run page, Tenant health (per tenant) and the Reconciliation comparison. A scoped audit's own score covers only its scope. The score is never changed by ignoring an issue.

Manifest status values

RAGGuard reads the manifest's processing_status column (or whichever column you map to it). Matching ignores capital letters and spaces at the ends. Any other value is treated as unknown: neither success, nor in flight, nor failed.

GroupValues it recognisesEffect
Successsuccess, succeeded, indexed, completed, complete, done, ready, ok, processed, trueThe pipeline "claims success". A document with no vectors then gets Critical instead of High. (true lets you map a true/false column such as is_indexed.) An indexed chunk count above 0 also counts as claiming success for a missing document.
In flightpending, queued, processing, running, in_progress, indexing, parsing, embeddingA document in one of these states that was updated within the grace period is Pending, not broken. A document stuck in one of them for longer is flagged, and the issue text says since when.
Failedfailed, error, errored, failureExplains a missing document ("marked ... and never retried successfully"). A document that is indexed although the manifest says failed gets the low problem status_failed_but_indexed.
Deleteddeleted, tombstoned, removedA manifest row with one of these for a document that is gone does not raise an Orphan manifest row issue

Settings groups and fields

There are seven settings groups. The detailed fields, help and examples are in the chapters linked in the first column. Secret fields are encrypted when stored, are write-only (after saving, the form says "A value is saved" and never shows the value), and can be left empty to keep the stored value. Optional text fields that you leave empty use the default. Text fields have length limits (for example 255 characters for Bucket and 4,000 for the JSON fields), and a message tells you when you exceed one.

Every address you enter (S3 endpoint, Qdrant URL, database host, repair webhook, alert webhook) must be a public one in hosted mode.

Glossary

TermMeaning
Access-control hash (ACL hash)A fingerprint of a document's permissions. RAGGuard compares the one in the manifest with the one on the vectors.
API keyA token (ragi_...) for scripts and CI. Shown once, stored only as a hash, works inside one workspace.
AuditOne comparison of source, manifest and index. It produces issues, document statuses and a health score.
ChunkA piece of a document that is turned into one vector
CollectionA named set of vectors inside Qdrant
Collection-level findingA finding about a whole collection, not about one document
Document idThe stable identity of a document, taken from the S3 key (after the prefix and key pattern), the manifest document_id column and the payload document_id field. It must be written the same way in all three.
Embedding / vectorThe list of numbers that represents a chunk for similarity search
ETagAn identifier S3 gives each object. For objects uploaded in several parts it is not a content hash, so RAGGuard flags it as unreliable.
EvidenceThe values an audit read from your systems when it raised an issue
FingerprintThe setup used to build a document's vectors: parser, chunking, embedding model and preprocessing
Grace periodHow long a recently changed or still-processing document is allowed to be Pending before it is judged. Default 10 minutes.
Health scoreThe share of healthy (and pending) documents, as a percentage
HMACA signature computed with a shared secret. RAGGuard signs each request to your worker, and your worker signs its callback.
IndexThe vector database your application searches (Qdrant)
IssueOne recorded disagreement, with a type, a severity, evidence and a recommended fix
Issue ledgerRAGGuard's own database of runs, issues, document states and plans. It never stores document contents.
Key patternThe regular expression that turns an S3 key into a tenant and a document id
Key prefixOnly keys under this prefix are audited
ManifestThe table where your pipeline records what it processed
OrphanSomething that no longer has an owner: vectors for a deleted document, or a manifest row for one
PayloadThe metadata stored with each vector (document id, hash, chunk id, and so on)
PendingA document that changed or is being processed within the grace period, so it is not judged yet
Pipeline driftVectors built with a different setup than your target pipeline
PointOne stored vector with its payload, in Qdrant
Probe (retrieval probe)A search against the live index, using one affected chunk's own vector, to show whether bad content can really be returned
Public addressA host that is reachable from the internet. Hosted mode refuses private network and localhost addresses.
RAGRetrieval-augmented generation: answers are written from documents retrieved from a vector index
Read-onlyRAGGuard only lists, reads and queries your systems. It never writes or deletes.
Repair planA set of documents with the smallest safe action for each, which RAGGuard hands to your worker and then verifies
ScopeThe part of the corpus an audit covers: everything, one tenant, or specific documents
SessionYour signed-in browser connection, kept in a cookie
source_hashThe SHA-256 of a document as your pipeline last processed it. RAGGuard compares it with the hash read from S3.
SourceThe documents in S3 that should be searchable
Target pipelineThe setup you expect documents to have been processed with, set in Settings
TenantA customer or business unit whose documents must stay separate
WebhookAn address that receives an automatic HTTP request. RAGGuard uses one for repairs and one for alerts.
WorkerYour own program that re-indexes documents when RAGGuard asks
WorkspaceOne account's private area: its connections, issues, history and plans
