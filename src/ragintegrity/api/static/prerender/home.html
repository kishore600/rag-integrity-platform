The problem

Your pipeline says success. Your users get the wrong answer.

A RAG system can fail silently while every background job reports success. The app keeps running, and nobody finds out until an answer is wrong.

  • Documents that were never embedded

    The file sits in storage, but nothing about it is searchable.

  • Updated documents with old vectors

    The source changed. The index keeps serving the previous version with full confidence.

  • Deleted documents that stay searchable

    Withdrawn or deleted content can still be returned to your users.

  • Half-indexed documents

    Only some chunks made it in, so answers are quietly incomplete.

  • Duplicates and empty vectors

    Retries double-count chunks. Zero vectors can never be retrieved.

  • Drift nobody planned

    The embedding model, the chunking or the permissions changed. Old documents did not.

How it works

Your documents and your index, one version of the truth

Your documents and your index should agree, and so should your manifest if you keep one. RAGGuard checks that they do, continuously.

  1. 1

    Connect, read-only

    Point RAGGuard at your S3 bucket and your vector index, in Qdrant or pgvector. Add the manifest table your pipeline writes to, if you have one, for extra checks. It only ever lists, reads and queries.

  2. 2

    Reconcile

    Every document is compared across the systems you connected, chunk by chunk. Retrieval probes check whether bad content can actually be returned to a user.

  3. 3

    Repair and verify

    Plans go to your own worker as signed requests. RAGGuard then checks the real index again. Old vectors are removed only after you approve.

Security

Safe to point at production

You are giving a verifier access to the systems behind your product. It is built to ask for as little as it can.

  • Read-only by design

    RAGGuard lists, reads and queries. It never writes to your S3 bucket, your manifest or your index.

  • Credentials stay secret

    Encrypted before they are stored, used only to read your systems, and never shown again after you save them.

  • Workspaces are isolated

    Every query is scoped to your workspace, so one account can never see another's data.

  • Private networks blocked

    The hosted service only connects to public addresses, so it cannot be pointed at internal services.

  • Signed repairs, approved removals

    Repair requests are signed with HMAC-SHA256, and vectors are removed only after you approve.

  • Hardened sessions

    HttpOnly cookies, rate-limited sign-in, scoped API keys and a strict content security policy.

FAQ

Questions, answered

The usual worries, answered plainly.

Does RAGGuard change my data?+

No. It only lists, reads and queries your S3 bucket, your vector index and, if you connect one, your manifest table. Fixes are carried out by your own worker, which RAGGuard asks with a signed request. RAGGuard then checks the real index again.

What do I need to connect?+

Two things: an S3 bucket with your source documents, and your vector index, either a Qdrant collection or a pgvector table in PostgreSQL. A manifest table, where your ingestion pipeline records what it indexed, is optional and adds extra checks. The Data Sources page tests each connection and tells you exactly what to change.

How does it know what my index should contain?+

It compares the content hash of each file in your source with the hash stored on its vectors. If you connect a manifest, it also compares the chunk counts your pipeline recorded with what is actually indexed. It can also run a search to check whether bad content can really be returned.

Can I run audits from CI or on a schedule?+

Yes. Create an API key and call the audit endpoint from GitHub Actions, cron or any scheduler. A key can run audits and read results, but it cannot read your settings or create other keys.

How are my credentials protected?+

They are encrypted before they are stored, used only from the server to read your systems, and never shown again once saved. The hosted service refuses private and localhost addresses.
